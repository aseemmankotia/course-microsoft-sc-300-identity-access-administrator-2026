## Chapter 7: App Registrations, Service Principals & API Permissions — Flashcards

| # | Front (Question) | Back (Answer) |
|---|-----------------|---------------|
| 1 | Maximum validity period for a client secret on an app registration? | 24 months (2 years) max in the Azure portal. Exam tip: certificates are the recommended stronger alternative for production workloads — secrets are easier to leak. |
| 2 | Default expiration for an admin consent request submitted via the admin consent workflow? | 30 days by default (configurable 1–365 days). Exam tip: workflow must be explicitly enabled and reviewers assigned before users can submit requests. |
| 3 | Default maximum number of app registrations a single non-admin user can create in a tenant? | 250. Exam tip: this is a tenant-level default quota an admin can raise or lower via the 'Users can register applications' / app registration restriction settings. |
| 4 | Delegated permission vs Application permission — key exam difference? | Delegated: app acts ON BEHALF OF a signed-in user, access capped by that user's own privileges. Application: app acts AS ITSELF with no signed-in user, always requires admin consent, full scope of the permission granted. |
| 5 | App registration vs Enterprise application — what's the actual relationship? | App registration creates an Application object (global, home tenant only) AND a Service Principal (shown as Enterprise Application) in the home tenant. A new Service Principal is created in each additional tenant that consents to use the app. |
| 6 | The four sign-in audience (supported account type) options at app registration? | 1) AzureADMyOrg (single tenant), 2) AzureADMultipleOrgs (multi-tenant), 3) AzureADandPersonalMicrosoftAccount (multi-tenant + personal MSA), 4) PersonalMicrosoftAccount (personal MSA only). Exam tip: SaaS apps for external tenants must use option 2 or 3. |
| 7 | Certificate vs Client Secret for app authentication — which does the exam prefer as best practice? | Certificate. It's asymmetric, harder to exfiltrate, and typically supports longer/rotatable validity. Exam trap: choosing 'client secret' as the 'more secure' answer when a scenario emphasizes security is wrong. |
| 8 | Three types of service principals in Azure AD? | 1) Application (tied to an app registration), 2) Managed Identity (auto-managed identity for Azure resources), 3) Legacy (pre-app-registration-model, created before app registration concept existed). |
| 9 | Three tenant-wide user consent setting options? | 1) Do not allow user consent, 2) Allow user consent for apps from verified publishers / low-risk permissions, 3) Allow user consent for all apps. Exam tip: option 2 is the balanced/recommended middle ground. |
| 10 | What claim in the issued token contains a user's assigned app roles for a given application? | The 'roles' claim. Exam tip: app roles are defined in the app registration manifest (appRoles) but ASSIGNED to users/groups on the Enterprise Application (service principal) object. |
| 11 | Azure CLI command to create an app registration + service principal in one step for RBAC? | az ad sp create-for-rbac --name <app-name>. Exam tip: this creates both the app registration and its service principal, and outputs an appId/password for authentication. |
| 12 | Which Azure AD roles can be assigned as reviewers in the admin consent workflow? | Global Administrator, Cloud Application Administrator, Application Administrator (or any user/group specifically designated as a reviewer). Exam tip: at least one reviewer must be configured or the workflow won't function. |
